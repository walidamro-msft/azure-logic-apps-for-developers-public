Lab 03: Order Fulfillment

Build a local Standard workflow that validates an order, routes inventory decisions, and returns an auditable result.

Visual Studio CodeStandard~55 min

Scenario and Objectives

An order API must reject invalid requests, reserve in-stock orders, and route unavailable inventory for review. In this lab, Compose actions stand in for external systems so the orchestration can run entirely on your machine.

  • Create a Logic Apps Standard project and stateful workflow.
  • Use conditions, scopes, variables, and run-after behavior.
  • Run and debug the workflow locally.
  • Separate workflow orchestration from replaceable integration boundaries.

Prerequisites

  • Visual Studio Code with the Azure Logic Apps (Standard) extension.
  • Azure Functions Core Tools v4 and the runtime required by the extension.
  • Azurite if your local Standard runtime configuration uses local Azure Storage.
  • A parent folder outside this workshop repository where the extension can create the generated workspace.
Important: VS Code local development is for Logic Apps Standard. Do not create a Consumption resource for this lab.

Build the Fulfillment Flow

New designer: Add Initialize variables at the workflow's top level. It cannot be added inside a condition branch or scope. After initialization, use Set variable whenever a branch needs to change the value. The labels or placement can differ in the old designer.
  1. Immediately after the HTTP trigger and before the condition, select Add an action, search for Initialize variables, and add the built-in action. Under Variables, set Name to fulfillmentStatus, Type to String, and Value to pending.
    View screenshot
  2. Below Initialize variables, add a Condition named Order is valid. Configure its single condition row as follows:
    1. Select the left Choose a value field, then select the fx icon to open the Expression editor window. Paste the expression below into that window without a leading @, and select Add. The field should show a purple fx and(...) token. Do not paste the expression directly into the field.
    2. Set the operator to is equal to.
    3. In the right Choose a value field, open Expression, enter true, and select Add. Use the Boolean expression true, not the text string "true".
    and(not(empty(triggerBody()?['orderId'])), not(empty(triggerBody()?['customerId'])), greater(int(triggerBody()?['quantity']), 0), greaterOrEquals(int(triggerBody()?['availableStock']), 0))

    Copy the expression as a single line. You do not need to add these four checks as separate condition rows. The and(...) expression returns one Boolean result.

    Verify before continuing: Order is valid must contain the complete and(...) expression above. Do not use the availableStock versus quantity expression here; that comparison belongs only in the nested Inventory is available condition.
    Expression, not text: In a workflow definition, a value that starts with @ is evaluated as an expression; without the @, it is plain text. The designer adds the @ only when you enter the expression in the Expression editor window, which then shows a purple fx and(...) token. If you paste or type the expression directly into the value field, the designer saves it as text without the @, the condition is always false, and every order returns 400. Do not type the @ yourself in the Expression editor; if you do, it reports The expression is invalid. To confirm, open the condition's Code preview tab: the left value must start with "@and(, and the right value must be true without quotation marks.
    View screenshot
  3. In the False branch, add a Response action and rename it Rejected Response. Set Status Code to 400, then copy this JSON into Body: 
    {
  "status": "rejected",
  "reason": "Invalid order"
}

    Before leaving the action, confirm that both Status Code and Body remain populated after the designer saves.

    View screenshot
  4. Build the inventory check inside the True branch:
    1. Select the + in the True branch, select Add an action, search for Scope, and add the built-in Control Scope action.
    2. Rename the Scope action to Try fulfillment. The scope groups the inventory decision so its overall success or failure can be handled later.
      View screenshot
    3. Select Add an action inside the scope, search for Condition, and add the built-in Control Condition action.
    4. Rename the nested condition to Inventory is available.
    5. In the condition's left Choose a value field, open Expression and copy: 
      int(triggerBody()?['availableStock'])
    6. Set the operator to is greater than or equal to.
    7. In the right Choose a value field, open Expression and copy: 
      int(triggerBody()?['quantity'])

    The condition follows the True branch when available stock is at least the requested quantity; otherwise, it follows the False branch.

    View screenshot
  5. In the inventory True branch, add Set variable and rename it Set fulfillmentStatus variable to confirmed. Select fulfillmentStatus for Name, and set Value to confirmed.
    View screenshot
  6. In the inventory False branch, add another Set variable and rename it Set fulfillmentStatus variable to manual-review. Select fulfillmentStatus for Name, and set Value to manual-review.
    View screenshot
  7. Add the success response outside Try fulfillment but still inside the outer Order is valid True branch. Select the + directly below the orange boundary of the entire Try fulfillment scope, then add a Response action and rename it Order is valid Response. Do not select a + inside the scope. The Response card must appear below, not within, the orange scope boundary. Leave its default run-after behavior as is successful, set Status Code to 200, and copy this JSON into Body: 
    {
  "orderId": "@{triggerBody()?['orderId']}",
  "status": "@{variables('fulfillmentStatus')}",
  "runId": "@{workflow()?['run']?['name']}"
}
    View screenshot
  8. Add the failure handler between the Try fulfillment scope and the 200 Response, as a parallel sibling of that Response:
    1. Select the + between Try fulfillment and the 200 Response. Make sure this + is outside the orange Try fulfillment boundary.
    2. Select Add a parallel branch.
      View screenshot
    3. In the new branch, select Add an action, search for Scope, add the built-in Control Scope, and rename it Handle failure.
      View screenshot
    4. Open Handle failure settings and select Run after. Clear is successful, select has failed and has timed out, and save the settings. These statuses apply to Try fulfillment.
      View screenshot
    5. Inside Handle failure, add a Response action, rename it Failure Response, and set Status Code to 500. Copy this JSON into Body: 
      {
  "status": "failed",
  "reason": "Order fulfillment failed"
}
      View screenshot
  9. Save the workflow and compare it with the completed design. Order is valid Response and Handle failure must be parallel siblings below Try fulfillment, inside the True branch of Order is valid.

Run Locally

Where to run the test commands: Do not paste them into the designer or the terminal running the host. Use a second PowerShell terminal and leave the host terminal running.
  1. Save the workflow. If your local settings use Azurite, start Azurite before continuing.
  2. In the VS Code window containing order-fulfillment-workspace, press F5. If VS Code asks which configuration to run, select the generated Logic Apps project configuration.
  3. Open the bottom Terminal panel. Wait until the host reports that it started, and then leave this terminal running.
  4. In the Terminal panel, select the + to open a second PowerShell terminal.
  5. In the second terminal, run the following setup once. The local management endpoint returns the signed callback URL required to invoke the HTTP trigger. The helper sends a payload and displays both the HTTP status and response body, including expected error responses. 
    $managementUri = 'http://localhost:7071/runtime/webhooks/workflow/api/management/workflows/wf-order-fulfillment/triggers/When_an_HTTP_request_is_received/listCallbackUrl?api-version=2022-05-01'

$callbackUri = (Invoke-RestMethod `
  -Uri $managementUri `
  -Method Post
).value

function Invoke-OrderWorkflow {
  param([hashtable]$Payload)

  $body = $Payload | ConvertTo-Json

  try {
    $response = Invoke-WebRequest `
      -Uri $callbackUri `
      -Method Post `
      -ContentType 'application/json' `
      -Body $body

    [pscustomobject]@{
      StatusCode = [int]$response.StatusCode
      ResponseBody = $response.Content
    } | Format-List
  }
  catch {
    $responseBody = $_.ErrorDetails.Message

    if ([string]::IsNullOrWhiteSpace($responseBody) -and $_.Exception.Response.Content) {
      $responseBody = $_.Exception.Response.Content.ReadAsStringAsync().GetAwaiter().GetResult()
    }

    if ([string]::IsNullOrWhiteSpace($responseBody) -and $_.Exception.Response.GetResponseStream) {
      $reader = [System.IO.StreamReader]::new($_.Exception.Response.GetResponseStream())
      try {
        $responseBody = $reader.ReadToEnd()
      }
      finally {
        $reader.Dispose()
      }
    }

    [pscustomobject]@{
      StatusCode = [int]$_.Exception.Response.StatusCode
      ResponseBody = $responseBody
    } | Format-List
  }
}
  6. The setup prints nothing when it succeeds; it only stores the callback URL and defines the helper. To confirm, run: 
    $callbackUri

    The output should start with http://localhost:7071/api/wf-order-fulfillment/triggers/When_an_HTTP_request_is_received/invoke and end with a sig= value. If it is empty, the callback URL lookup failed; review the error above it and see Troubleshooting.

  7. Keep the second terminal open and run each test separately. The workflow runs only when you run a test command.

Test 1: Confirmed order

Run:

Invoke-OrderWorkflow -Payload @{
  orderId = 'ORD-1001'
  customerId = 'C-42'
  quantity = 2
  availableStock = 8
}

The status code should be 200, and the response body should contain the status confirmed.

Test 2: Manual review

Run:

$body = @{
  orderId = 'ORD-1002'
  customerId = 'C-42'
  quantity = 10
  availableStock = 3
} | ConvertTo-Json

try {
  $response = Invoke-WebRequest `
    -Uri $callbackUri `
    -Method Post `
    -ContentType 'application/json' `
    -Body $body

  [pscustomobject]@{
    StatusCode = [int]$response.StatusCode
    ResponseBody = $response.Content
  } | Format-List
}
catch {
  [pscustomobject]@{
    StatusCode = [int]$_.Exception.Response.StatusCode
    ResponseBody = $_.ErrorDetails.Message
  } | Format-List
}

The status code should be 200, and the response body should contain "orderId":"ORD-1002" and "status":"manual-review".

Test 3: Rejected order

Confirm the JSON response first: In the designer, open the False branch of Order is valid and select Rejected Response. Set Status Code to 400. In Body, enter the JSON below, save the workflow, and confirm the Body remains populated after the save. 
{
  "status": "rejected",
  "reason": "Invalid order"
}

Run:

Invoke-OrderWorkflow -Payload @{
  orderId = ''
  customerId = 'C-42'
  quantity = 0
  availableStock = 3
}

The output should show StatusCode : 400 and ResponseBody : {"status":"rejected","reason":"Invalid order"}. If the status is 400 but the body is still empty, reopen the rejected run in local run history and inspect the False-branch Response action's inputs to confirm that its Body was saved.

After each request, inspect the host terminal for the new run. You can also open the workflow's local run history from the Logic Apps extension to inspect action inputs, outputs, skipped branches, and scope status.

Validation Checklist

  • The first payload returns confirmed.
  • The second payload returns manual-review.
  • The third payload returns HTTP 400.
  • Each 200 response contains a unique run ID.
  • The failure scope remains skipped during successful tests.

To exercise failure handling, temporarily add a Compose action inside Try fulfillment with an expression that fails at runtime, such as int('abc'), run once, confirm the 500 response, and then remove the deliberate fault.

Troubleshooting

SymptomCheck
F5 appears to do nothingSave the workflow, make sure you are in the new VS Code window that contains order-fulfillment-workspace, then open View > Terminal and check the generated task terminal for startup output.
Host does not startConfirm Core Tools v4, extension prerequisites, and storage settings; start Azurite if configured.
Callback URL lookup failsConfirm the workflow and trigger names match the names in $managementUri, and verify that the local host finished starting on port 7071. Review the host terminal for an earlier startup error.
Saving shows "Failed to configure MSI permissions for connections"You can ignore this notification in this lab. After saving, the extension tries to set up managed identity access for Azure-hosted connectors. Because you selected Skip for now, no Azure connection exists to configure. The workflow is still saved; confirm that workflow.json shows your latest change.
A valid order (Test 1) returns 400 rejectedThe Order is valid expression was saved as text. Open its Code preview tab: if the left value is "and(..." instead of "@and(...", delete it, re-add it using the fx Expression editor, and do the same for the Inventory is available values (@int(...)). Save the workflow and restart the host.
HTTP 400 has an empty bodyOpen the False-branch Response action and restore its JSON Body. Save the workflow, confirm the Body remains populated, and run the rejected-order test again.
Designer cannot loadOpen the workspace root rather than only the workflow folder, then restart the extension host.
Two responses try to runReview run-after settings so success and failure responses are mutually exclusive.
