Lab 07: Reusable Workflows

Build a common customer eligibility workflow, call it from an order workflow, and continue according to the returned decision.

Azure portalStandard only~60 min2 stateful workflows

Scenario and Objectives

Order intake, quote creation, and subscription renewal all need the same check: does this customer exist, and is their account active? Instead of copying the rule into each workflow, expose it once as a shared workflow with a small request-response contract.

In this lab, create exactly two workflows in one Azure Logic Apps Standard resource, entirely in the Azure portal:

WorkflowRoleResponsibility
common-customer-eligibilityShared childNormalize a customer ID, look up demo customer data, and return a Boolean eligibility decision with a reason.
submit-orderParent / callerReceive an order, call the child, then prepare fulfillment or reject the order based on the child's response.
  • Separate a reusable business capability from caller-specific processing.
  • Use the built-in Workflow Operations action rather than copying a callback URL.
  • Pass only the child's required input and consume its typed response.
  • Distinguish a business rejection from a failed or timed-out workflow call.
  • Trace the parent and child runs in the portal.
Lab boundary: customer records are synthetic data in a Compose action. Fulfillment is another Compose action, not an actual inventory reservation, payment, or database write. No CRM, managed connector connection, or custom code is required. A production implementation would replace the demo lookup with an authorized customer-system call.

The child knows nothing about orders. It can serve other workflows in the same Standard resource without duplicating customer rules. Only the parent decides what eligibility means for order processing.

Prerequisites and Resource Setup

  • A non-production Azure subscription and permission to create or edit a Standard logic app and its supporting resources.
  • Access to the Azure portal. All authoring and required tests use the portal; VS Code and a local runtime are not needed.
  • A dedicated lab resource group, or an existing portal-editable Standard logic app. Do not use a production app or a read-only app deployed from a package.
  1. If you already have a suitable Standard logic app, open it and skip resource creation. Otherwise, search for Logic apps in the portal and select Create.
  2. Select Standard (Workflow Service Plan), not Consumption. Choose your lab subscription, resource group, region, and a unique app name such as la-shared-workflows-<suffix>.
  3. Select or create a Windows Workflow Service Plan, using WS1 for this small lab if allowed by your subscription. On the storage settings tab, select or create the required storage account. Follow your organization's networking and monitoring policies, review the estimated cost, and select Review + create, then Create.
  4. After deployment, open the resource. Under Workflows, select Workflows. You will add both workflows here, not create a second logic app resource.
Cost: a Standard plan has provisioned compute charges even when workflows are idle; storage and monitoring can also incur charges. Reuse an approved lab app when practical. Disabling a workflow does not remove the plan's cost.
Why stateful? choose Stateful for both workflows so their run histories are available for this exercise. This is a lab choice, not a requirement that every reusable workflow be stateful.

Define the Shared Contract

The child accepts one string, customerId. It trims surrounding whitespace and converts the ID to uppercase before lookup. Its response always contains these fields when the check completes:

FieldTypeMeaning
customerIdstringThe normalized customer ID.
eligibleBooleantrue only when the customer exists and has status Active.
reasonstringEligible, CustomerBlocked, or CustomerNotFound for the demo data.

The child returns HTTP 200 for both eligible and ineligible customers: it successfully answered the business question. The parent must inspect eligible, not treat a successful action as permission to process an order. Invocation failures and invalid response shapes follow a separate 503 path.

Expression entry: for a single expression, open the field's Expression (fx) editor and enter the expression shown without a leading @. For the JSON Body examples below, paste the complete object; full-value strings such as "@equals(...)" are workflow expressions and preserve the Boolean or object type. Do not change them to "@{equals(...)}", which interpolates a string. Inspect Code view or Code preview to confirm the saved values if the designer turns them into tokens.

1. Build the Common Workflow

  1. From the Standard app's workflow list, select Add. Name the workflow common-customer-eligibility, choose Stateful, and create it. Open the workflow's Designer.
  2. Add the built-in Request trigger When an HTTP request is received. Set Method to POST (under advanced parameters if necessary). Leave the relative path empty. Paste this into Request Body JSON Schema: 
    {
  "type": "object",
  "properties": {
    "customerId": { "type": "string" }
  },
  "required": ["customerId"]
}
  3. Add Data Operations > Compose and rename it Normalize customer ID. In Inputs, use the Expression editor: 
    toUpper(trim(triggerBody()?['customerId']))
  4. Add another Compose action named Customer directory. Paste this JSON object into Inputs: 
    {
  "CUST-100": { "status": "Active" },
  "CUST-200": { "status": "Blocked" }
}

    Keep this as an object, not a quoted JSON string. These two records make the lab repeatable without connecting to a real customer system.

  5. Add a Compose action named Customer record. In Inputs, enter this expression: 
    outputs('Customer_directory')?[outputs('Normalize_customer_ID')]

    The dynamic key selects the normalized customer's record. The ? safely returns null if the ID is absent, allowing an explicit CustomerNotFound decision.

  6. Add the built-in Request Response action and rename it Return eligibility. Set Status Code to 200, add the header Content-Type with value application/json, and paste this into Body: 
    {
  "customerId": "@outputs('Normalize_customer_ID')",
  "eligible": "@equals(outputs('Customer_record')?['status'], 'Active')",
  "reason": "@if(empty(outputs('Customer_record')), 'CustomerNotFound', if(equals(outputs('Customer_record')?['status'], 'Active'), 'Eligible', 'CustomerBlocked'))"
}

    Keep Asynchronous response off in the Response settings if that option is shown. The parent needs the result, not an early acknowledgement. Keep the Response as the last action.

  7. Save the workflow. If your designer uses drafts, also Publish it. The parent must call the saved, published child, not an unpublished draft.
Names matter: spaces in display names become underscores in expression references. The names above produce Normalize_customer_ID, Customer_directory, and Customer_record. Rename actions before adding dependent expressions, and verify these names in Code view.

Quick child check

Use the designer's Run with payload option (or the payload option beside Run). Set Content-Type to application/json and send:

{
  "customerId": " cust-100 "
}

In the workflow's Run history, open the run and inspect Return eligibility. Its evaluated response body should be:

{
  "customerId": "CUST-100",
  "eligible": true,
  "reason": "Eligible"
}

If your portal offers Run draft with payload, you can use it for this isolated check, but publish the child before continuing. A plain Run without a payload is not equivalent to this test.

2. Build the Calling Workflow

  1. Return to the same Standard app's workflow list. Add a second Stateful workflow named submit-order, then open its Designer.
  2. Add When an HTTP request is received, set Method to POST, and paste this into Request Body JSON Schema: 
    {
  "type": "object",
  "properties": {
    "orderId": { "type": "string" },
    "customerId": { "type": "string" }
  },
  "required": ["orderId", "customerId"]
}
  3. Add Control > Scope and rename it Check customer. This scope will contain the workflow call and response parsing, so either failure can use the same error path.
  4. Inside the scope, add the built-in Workflow Operations > Call workflow in this logic app action. Some designers label it Invoke a workflow in this workflow app. Rename it Call customer eligibility and select common-customer-eligibility under Workflow Name.

    Set the action's Headers to include Content-Type: application/json. In its Body, pass only the shared contract:

    {
  "customerId": "@triggerBody()?['customerId']"
}

    If the designer expands the request schema into input fields, populate customerId with the parent trigger's customerId token instead. Do not pass orderId: the common workflow should not depend on order-specific data.

  5. Still inside Check customer, after the call, add Data Operations > Parse JSON and rename it Parse eligibility. Set Content using this expression: 
    body('Call_customer_eligibility')

    Paste the following into Schema. This validates the returned contract and exposes typed tokens to later actions:

    {
  "type": "object",
  "properties": {
    "customerId": { "type": "string" },
    "eligible": { "type": "boolean" },
    "reason": { "type": "string" }
  },
  "required": ["customerId", "eligible", "reason"]
}
Use the local workflow action: do not select a generic HTTP action or the Consumption workflow picker. The built-in operation selects a workflow in this Standard resource without storing its callback URL or SAS signature. Both workflows must be in the same resource and the child must have a Request trigger.

3. Continue Based on the Child's Response

  1. After and outside Check customer, add a Control > Condition action named Customer is eligible. Keep its Run after for Check customer set to Is successful only.
  2. In the condition's left field, use the Expression editor to enter: 
    body('Parse_eligibility')?['eligible']

    Choose is equal to. For the right field, use the Expression editor to enter true as a Boolean, not the text "true". In Code preview, the comparison should resemble "equals": ["@body('Parse_eligibility')?['eligible']", true].

  3. In the True branch, add a Compose action named Prepare fulfillment with this object in Inputs: 
    {
  "orderId": "@triggerBody()?['orderId']",
  "customerId": "@body('Parse_eligibility')?['customerId']",
  "status": "ReadyForFulfillment",
  "nextAction": "ReserveInventory"
}

    This is the parent's next processing step after eligibility succeeds. It uses the normalized customer ID returned by the child, rather than the unnormalized trigger value. Inventory is not actually reserved.

  4. After that Compose, still in the True branch, add a Response named Order ready. Set status 200, header Content-Type: application/json, and Body using the Expression editor: 
    outputs('Prepare_fulfillment')
  5. In the False branch, add a Response named Order rejected. Set status 400, header Content-Type: application/json, and this Body: 
    {
  "orderId": "@triggerBody()?['orderId']",
  "customerId": "@body('Parse_eligibility')?['customerId']",
  "status": "Rejected",
  "reason": "@body('Parse_eligibility')?['reason']"
}
  6. Add a parallel branch directly after Check customer, alongside the condition, containing a Response named Eligibility unavailable. Set status 503, header Content-Type: application/json, and this Body: 
    {
  "orderId": "@triggerBody()?['orderId']",
  "status": "EligibilityUnavailable",
  "message": "The customer check could not be completed. Retry later.",
  "runId": "@workflow()?['run']?['name']"
}

    Open this Response's Settings > Run after. Select Check customer as its predecessor and enable Has failed and Has timed out only. Clear Is successful and Is skipped. Do not attach this response after Order ready or Order rejected.

  7. Keep asynchronous response off for all three parent Response actions. Save and, if offered, Publish the parent. Confirm that the app's workflow list contains both enabled workflows.

Business result versus execution result

A blocked customer is a successful child execution with eligible: false, followed by the parent's 400 response. A disabled child, a failed call, or a malformed response is not a customer rejection: the parent must not prepare fulfillment and instead returns 503. Check the actual branch and response inputs, not just the overall run status.

4. Test Both Workflows Together

  1. Open submit-order in the portal. Use Run with payload, set Content-Type to application/json, and enter the first request below. If only Run draft with payload is available, the parent draft can be tested that way, but the child must already be published.
  2. Open the parent's Run history and select the new run. Expand Check customer. Inspect the call's inputs and outputs, then Parse eligibility and the condition's result.
  3. Open the child workflow's Run history in another portal tab. Inspect the corresponding run using the call's child-run link if available, or match the timestamp and normalized customer ID. Confirm that the child received only customerId and returned the documented contract.
  4. Inspect the executed parent Response action's evaluated Inputs to verify its status code and body. A portal run command may not display the HTTP response itself. Verify that only the intended Response executed and that Prepare fulfillment was skipped for rejections.
  5. Repeat with the blocked, unknown, and blank customer requests in the table.

Test a technical failure and restore the child

  1. After existing runs finish, open the common-customer-eligibility workflow's Overview and select Disable. Disable only this lab workflow, not the entire Standard app.
  2. Run submit-order again with the eligible request. Inspect Call customer eligibility; the disabled child cannot serve the request. Allow any configured call retries to finish.
  3. Verify that Check customer fails, Customer is eligible and fulfillment are skipped, and Eligibility unavailable executes with status 503 and a parent run ID. It must not return a business rejection or a ready-for-fulfillment result.
  4. Enable the child again and rerun the eligible request to confirm the 200 path is restored. Do not leave the shared workflow disabled.
Completion check: keep evidence of the child response and the parent's selected branch for all four business cases, plus the 503 failure and restored 200 path. Use synthetic data only. Do not include callback URLs, SAS signatures, or other credentials in screenshots or shared notes.

Troubleshooting

SymptomCheck
Child is missing from Workflow NameBoth workflows must belong to the same Standard resource. Save or publish the child's Request-trigger workflow first, enable it, then reopen the parent designer. Use Workflow Operations, not the Consumption action.
Call returns no eligibility bodyEnsure every normal child run reaches Return eligibility, with status 200 and asynchronous response off. A Request workflow without a Response does not supply the business result needed here.
Parse eligibility failsInspect the call's Body. It must be an object with a Boolean eligible, not a JSON string or "true". Use full-value @... expressions in response JSON, not string interpolation, and publish the corrected child.
Every order takes the False branchEnter the condition through the fx editor and compare to Boolean true. Check the normalized ID and the exact Active status in the demo data.
503 response is skipped on failureIts Run after must point directly to Check customer with Has failed and Has timed out selected. Keep the success condition on Is successful only.
Expression cannot find an actionVerify the internal names and nesting in Code view. Call customer eligibility and Parse eligibility belong inside Check customer; the condition is after that scope.
Portal does not allow editingUse a portal-editable lab app. Do not change package deployment settings on a shared or production app just to complete the exercise.

Cleanup and References

If you reused a shared lab app, remove only submit-order and common-customer-eligibility when no longer needed, after checking that no other workflow calls the child. Do not delete the shared app, plan, or storage account. If you created a dedicated resource group for this lab, delete it after confirming that all its resources are disposable.

For production, keep the contract stable, version breaking changes, secure Request endpoints, and replace the demo customer directory with a real system accessed using least privilege. Treat run history as potentially sensitive. The local workflow action avoids copying a callback URL, but it does not by itself remove or secure the child's HTTP endpoint.

Reuse discussion: a quote or renewal workflow could call the same child with a customerId and make its own decision from eligible and reason. You do not need to create those additional workflows in this lab. Keep order-specific fulfillment in the parent and shared customer policy in the child.
