Logic Apps Migration Agent

Use AI-assisted discovery, planning, and conversion to modernize existing integrations to Logic Apps Standard while retaining human review and business-behavior validation.

Logic Apps StandardVS Code + GitHub CopilotHuman-in-the-loop

Modernize Behavior, Not Legacy Topology

The Logic Apps Migration Agent is an open-source Visual Studio Code extension built on GitHub Copilot and the VS Code Language Model API. It helps inventory integration artifacts, understand dependencies, plan a target design, and generate a baseline Standard implementation.

This module draws on the Microsoft Community Hub article Modernize Any Integration Platform to Azure Logic Apps Standard with the Logic Apps Migration Agent, published May 7, 2026.

  • Preserve contracts, transformations, routing, ordering requirements, and error behavior.
  • Reconsider workflow boundaries, connector choices, identity, networking, and operations for the target platform.
  • Migrate one logical flow group or business capability at a time rather than attempting a big-bang conversion.
Not a one-click migration: generated artifacts are a starting point. Engineers and business owners still approve architecture, resolve capability gaps, and prove semantic equivalence.

Source Coverage and Target Scope

The article introduces BizTalk Server 2016 and 2020 as the initial fully implemented source platforms and describes extensibility for other products. Support evolves: the Microsoft Learn overview documents built-in BizTalk, MuleSoft, and basic TIBCO BusinessWorks parsing for version 1.12.1, with platform-specific limitations.

  • Check the installed release: confirm that its parsers cover your source versions, artifact types, and required transformations before estimating migration effort.
  • Parsing is not parity: discovering an artifact does not guarantee a correct generated implementation. Record unsupported components and manual redesign work explicitly.
  • Extensible, not universally automatic: other platforms can require custom parsers and platform-specific discovery, analysis, conversion, and validation guidance.
  • Standard target: plan for a Logic Apps Standard project, not a Consumption workflow. Select hosting and deployment support using the installed release documentation and the workshop's Standard Overview.

The Five-Stage Migration Workflow

Review each stage's evidence before approving the next. AI assistance accelerates repeatable work; it does not transfer accountability away from your team.

StageAgent-assisted workHuman review checkpoint
1. DiscoveryInventory artifacts, build dependency graphs, and identify flow groups and gaps.Confirm endpoints, shared dependencies, missing artifacts, and the actual business flow.
2. PlanningPropose target architecture, action mappings, artifact dispositions, and per-flow migration plans.Approve workflow boundaries, connector choices, gap resolutions, and acceptance criteria.
3. ConversionExecute the approved task plan to generate Standard workflows, connections, and supporting files.Inspect generated logic, configuration, transformations, and custom code; resolve unsupported behavior.
4. ValidationHelp test generated workflows against source specifications and supplied test cases.Compare observable behavior, failure handling, and side effects; resolve differences before deployment.
5. DeploymentPrepare and deploy generated artifacts using the supported deployment path.Approve the environment, access, costs, telemetry, release evidence, and rollback plan.

The specialized Copilot agents are @migration-analyser, @migration-planner, and @migration-converter. Use their outputs as reviewable engineering artifacts, not as proof of production readiness.

Prepare a Representative Pilot

  1. Choose one bounded, non-production integration with a known owner, representative dependencies, and documented expected behavior.
  2. Install VS Code, the Logic Apps Migration Agent, and the required Logic Apps Standard tooling. Confirm GitHub Copilot access and the current extension requirements; local testing and deployment can need additional tools.
  3. Collect source projects, bindings, schemas, maps, pipelines, orchestrations, custom code, configuration references, and test specifications in an organized source directory.
  4. Remove embedded secrets and sanitize sample data. Use certificate and secret references rather than private keys or production credentials, and follow organizational policies for AI-assisted source processing.
  5. Open the extension in VS Code and select the source directory, or run Logic Apps Migration Agent: Select Source Folder from the Command Palette.
  6. Review discovery and planning outputs before authorizing conversion. Configure an isolated Azure environment only when ready to test or deploy; review generated resources and costs first.

Workshop Exercise: Prove One Flow

Use a sanitized order-processing integration as a discussion exercise, or use your own approved source project for a guided pilot. A local source project and the extension are required to execute the migration; this workshop does not include a legacy-platform export.

  1. Capture the contract: document the incoming order schema, validation rules, routing decision, transformed output, response, and downstream side effects.
  2. Review the plan: identify the proposed trigger, connectors, transformation approach, retry policy, and failure path. Record every gap and its owner.
  3. Convert and inspect: check that the generated Standard project implements the approved plan and uses environment-specific connection settings rather than hard-coded credentials.
  4. Compare results: run the same fixtures against the source behavior and target workflow in an isolated environment. Compare outputs and side effects, not only successful run status.
Test caseEvidence to capture
Valid orderExpected schema, field mappings, route, response, and exactly the intended downstream business effect.
Missing or invalid fieldEquivalent rejection and error response, without unintended downstream calls.
Duplicate or out-of-order messageRequired deduplication and ordering behavior, including correlation identifiers.
Downstream timeout or failureExpected retries, terminal failure handling, recovery path, and diagnostic evidence.

Exit criteria: a reviewed inventory and plan, an explicit gap list, passing behavior comparisons, and an agreed operational owner. Static results help isolate branches but do not replace live connector, security, performance, and end-to-end validation.

Production Readiness and Phased Cutover

  • Architecture and gaps: deliberately redesign unsupported capabilities using appropriate connectors, custom code, Functions, Service Bus, or API Management. Do not copy legacy topology solely for visual similarity.
  • Security and operations: validate managed identity, least privilege, secret storage, network access, throughput, cost, alerts, correlation, and recovery. See Security & Limits and Monitoring & Troubleshooting.
  • Release: version the reviewed source, generated artifacts, infrastructure, and test evidence. Follow the release pipeline guidance for controlled promotion.
  • Cutover: agree on coexistence, backlog reconciliation, partner coordination, in-flight messages, duplicate side effects, rollback, and eventual decommissioning before switching traffic.
Availability changes: the May 2026 article also previews upcoming platform features. Treat those announcements as historical context, not a guarantee of current connector availability, release status, or migration coverage.
