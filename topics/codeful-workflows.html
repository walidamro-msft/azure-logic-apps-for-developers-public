Codeful Workflows

Define the orchestration in C# with the Logic Apps Standard SDK, while retaining the Logic Apps runtime and visual run-history experience.

Logic Apps StandardC# + .NET SDKPreview: verify release support

A New Authoring Model, Not a New Runtime

Codeful Workflows, also described as code-first authoring or Code for Workflows, lets developers define triggers, actions, dependencies, and control flow in C# rather than primarily through the visual designer and JSON. The Microsoft.Azure.Workflows.Sdk package provides typed operations, IntelliSense, and fluent APIs for composing the workflow.

The SDK compiles the workflow definition for execution on the Logic Apps runtime. Developers change how they author the orchestration; operators still inspect workflow runs visually, including action inputs, outputs, and failures.

flowchart TD
    C["C# workflow definition"] --> B["SDK and project build"]
    B --> R["Logic Apps Standard runtime"]
    D["Designer-authored workflow"] --> R
    R --> H["Visual run history and diagnostics"]
Keep the choices separate: Codeful Workflows is an authoring option for Logic Apps Standard, not a hosting plan or a replacement for the stateful/stateless distinction. The SDK reference includes stateful, stateless, and agent factories; the workflow choices exposed by the workspace wizard depend on the installed release.

Source context: the May 20, 2025 announcement describes an early, pre-release Durable Task-based design. This module follows the later public SDK authoring guide and fluent API reference; do not combine the early function-based sample with SDK workflow-provider code as though they were one template.

Why Choose Code-First Authoring?

Familiar .NET development

Use C# tooling, IntelliSense, refactoring, and a .NET project structure to develop integrations alongside the team's other application code.

Maintainable composition

Organize larger orchestrations through named operations and reusable C# components rather than navigating an increasingly large designer canvas.

Readable code reviews

Review changes to operations, dependencies, and error paths in C#. Designer-authored JSON already supports source control; code-first offers a different representation for reviewing it.

Reuse and versioning

Factor common composition into shared helpers or versioned .NET packages where appropriate, with explicit contracts and tests instead of copied workflow fragments.

Decision rule: choose code-first when it improves how the owning team builds, reviews, reuses, and maintains the integration. A large action count alone is not a reason to migrate, and changing authoring style does not automatically improve runtime performance.

Codeful vs. Designer, Inline Code, and Functions

The important distinction is what the code defines: a processing step or the orchestration itself. VS Code is a tool for both designer-first and code-first Standard development; using VS Code does not by itself make a workflow codeful.

ApproachWhat it definesWhen it fits
Designer-first workflowOrchestration authored visually and represented in JSON.The workflow is clear in the designer, or maintainers need visual editing.
Codeful WorkflowsThe orchestration itself, composed in C# with SDK operations.A .NET team benefits from code-based composition, reviews, and reuse, and the required operations are supported.
Inline C# scriptCustom processing inside an Execute CSharp Script Code action.A designer-authored Standard workflow needs a bounded transformation or calculation. See Lab 06.
Local .NET functionA reusable custom-code step called by a workflow in the same Standard workspace.Keep the designer orchestration while organizing richer .NET processing alongside it.
Separate Azure Function or serviceAn external processing or API boundary.The code needs independent deployment, ownership, reuse, or scaling.

Keep a straightforward, working designer workflow unless there is a concrete maintenance benefit. For step-level extensions, start with Inline Code and Script Actions and Advanced Patterns.

Create a Code-First Workspace

Use Visual Studio Code with the Azure Logic Apps (Standard) extension and the .NET/local-runtime prerequisites linked from the SDK guide. Use an approved non-production Azure subscription for connector resources and deployment; those resources can incur charges.

  1. Open the Azure view. On the Workspace toolbar, open the Azure Logic Apps menu and select Create new logic app workspace.
  2. Provide the workspace folder, workspace name, logic app name, and workflow name.
  3. For the project flavor, select Logic app (codeful). Start with a Stateful workflow for a non-AI request-response example; check the current wizard for other supported choices.
  4. Review the configuration and select Create workspace. Trust the workspace only after verifying its source.
  5. When prompted, choose Use connectors from Azure, select the subscription and resource group, and configure only the connectors required for the example.
  6. Open the generated workflow C# file. For a managed connector action, hover over its call and choose Manage connector to select or create its connection.
Check support first: the linked public guide documents preview restrictions for service-provider connectors, authentication, and custom-code callbacks. Review Release Boundaries before selecting the example's connectors. Do not assume every operation from an existing designer workflow is available through the installed SDK.

Understand the Project and Configuration

The generated project is a .NET project, not just a collection of hand-edited workflow JSON files. Follow the generated template for your installed SDK version.

File or artifactResponsibility
Program.csConfigure and start the host, including workflow-provider registration.
Workflow .cs filesDefine and compose named triggers, actions, and dependencies.
.csprojRecord the target framework and package references, including the workflow SDK.
host.jsonConfigure runtime behavior.
connections.jsonRecord connector configuration and connection references.
local.settings.jsonHold local configuration, which can include credentials. Never commit it.

Externalize environment-specific values such as queue names and endpoints rather than hardcoding them into the orchestration. Review connection metadata before committing, keep secrets out of source control, and supply environment settings through the supported deployment configuration.

Define Operations, Then Compose the Flow

Use the SDK to construct an execution graph. This is not a feature that converts an arbitrary C# method into a durable workflow.

SDK entry pointPurpose
IWorkflowProviderProvide workflow definitions for host registration. Registration extensions include AddWorkflowProvider<T> and AddWorkflowProviders.
WorkflowFactoryCreate workflow definitions for supported workflow types.
WorkflowTriggers and WorkflowActionsCreate typed trigger and action operations, including supported managed connector operations.
Then() and Join()Compose dependencies and join execution paths. Configure non-success run-after paths explicitly.
WorkflowControlActionsDefine workflow controls such as Scope, Condition, ForEach, Until, Switch, and Terminate.
WorkflowContextAccess trigger and action results during custom-code execution, including typed results where supported.

This composition fragment shows the chaining pattern only. The variables represent operations that have already been created and named through the SDK; this is not a complete runnable workflow:

requestTrigger
    .Then(validateOrder)
    .Then(publishMessage)
    .Then(successResponse);

Follow the generated template and SDK reference for operation construction, provider registration, scopes, branches, and failure dependencies. Use custom-code callbacks for processing that needs ordinary C# logic, subject to the installed release's callback restrictions.

Definition time vs. run time: a C# loop that constructs the workflow definition is not a workflow ForEach operation. Use SDK workflow controls when the iterations need workflow scheduling, connector calls, retries, or per-action operational visibility.

Build, Run, Inspect, and Deploy

  1. Build and start locally: select Run > Start debugging (F5). The generated project compiles and starts the local Logic Apps runtime.
  2. Open Overview: use the Program.cs context menu's Overview entry. If the project contains multiple workflows, select the workflow to inspect.
  3. Trigger and inspect: execute the workflow from Overview or its supported trigger entry point. Inspect visual run history, action inputs and outputs, and failure paths.
  4. Iterate in C#: change the workflow source, rebuild, and rerun representative cases. Review the diff for changed dependencies, configuration, and error behavior, not only C# syntax.
  5. Deploy a built artifact: use the deployment experience supported by the generated project and installed release, or its supported CI/CD path. Provision connections, identities, networking, and environment settings deliberately; deploying source files alone is not a release process.
  6. Maintain the source of truth: make orchestration changes in the C# project, then rebuild and redeploy. The code-authored workflow's deployed visual representation is for inspection, not portal editing of its definition.
Visual operations remain: the public SDK guide confirms that code-authored workflows use the same rich visual run-history representation as designer-authored workflows. This does not imply two-way designer/C# editing or a guaranteed visual preview before execution.

Apply the existing release pipeline guidance and monitoring practices. Test live connector authentication and side effects in an isolated environment; a successful build or a green run against mocks does not prove end-to-end readiness.

Example Walkthrough: Request to Message

For a first demonstration, keep the business flow small: receive an HTTP request, validate an order and create a correlation identifier with custom C#, publish a message through a supported managed connector, and return a response. Add an explicit failure path rather than demonstrating only the happy path.

If you choose Service Bus, confirm the managed connector operation and authentication available in your release. Do not substitute a built-in service-provider operation solely because it exists in the designer.

CaseExpected evidence
Valid orderThe intended message is published, a successful response is returned, and the visual run shows the processing steps.
Invalid orderA clear validation response is returned without publishing a message.
Connector failure or timeoutThe configured failure path runs, success is not reported, and diagnostics retain a useful correlation identifier without exposing secrets.
Small source changeThe C# diff clearly shows the change, and rebuilding and rerunning confirms the expected behavior.

This is a demonstration outline, not an additional hands-on lab. Use it to compare the C# definition with the visual execution view and discuss which parts are reusable.

Release Boundaries and Preview Limitations

The linked public SDK guide identifies this as a preview feature. The table below summarizes that guide's documented restrictions, checked for this module on November 16, 2026; it is not a claim that every newer extension, SDK, or backend release has identical support.

AreaPublic guide's documented positionBefore teaching or adopting
Service-provider connectorsBuilt-in service-provider-based operations are unavailable in the documented preview; managed connectors are supported. This restriction is distinct from SDK built-in operations such as control flow.Verify the exact trigger/action and connector implementation in the target release.
Dynamic schemasUnavailable in the documented preview.Check operations that depend on runtime-selected schemas or generated inputs.
Custom-code actionsCallback methods are supported; inline lambda functions are unsupported in the documented preview.Use the generated callback pattern. A workshop showing newer lambda support is not proof that the installed SDK supports it.
Managed identitySupport is in development for the documented code-first connector experience; the guide directs preview users to connection keys.Confirm authentication support and organizational policy. If required managed identity is unavailable, choose another supported approach rather than weaken policy.
Operation referencesActions must be added and named before they can be referenced.Review operation names and dependencies as part of the workflow contract.

Later demonstrations can show capabilities beyond the published guide. Validate the installed extension, SDK package, backend support, and release notes together before relying on them. Do not present planned JSON conversion, pre-execution visual preview, broader connector coverage, or expanded C# expressions as universally released features.

Do not generalize preview restrictions: these checks concern the code-first SDK experience. They do not remove capabilities from existing designer-authored Standard workflows, and code-first authoring does not itself change hosting costs, concurrency limits, or runtime settings.
